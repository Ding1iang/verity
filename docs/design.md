# verity 设计说明

> 一句话：verity 是一套给 AI 编码代理用的交付验收技能包。它不教怎么写代码，只回答一个问题——当 AI 说“做完了”，凭什么？

## 1. 解决什么问题

AI 交付最常见的故障不是“不会做”，而是“没验却说验了”：截图只截到局部就断言整页正常；复用上一个版本的结论；测试没跑先写“应该没问题”；把“没试过”写成“阻塞”、把“未验证”写成“通过”；结论散落在对话、提交和文档里，同一件事三个口径。

verity 用五条硬约束堵住这些漏洞：任务卡先定靶、证据分级、v1 默认模板四状态与三包结论（检查器默认拒绝带欠账，历史账本用 `--compat-debt` 读取）、阻塞举证、单一账本。核心只有一句：**结论只能比证据小，不能比证据大。**

## 2. 四种模式

| 模式 | 什么时候用 | 主线 |
|---|---|---|
| 新功能 | 有明确需求，要给系统加能力 | 需求澄清 → 规格 → 计划 → 实现 → 验收 |
| 修缺陷 | 已有行为与预期不符 | 复现 → 日志定位 → 根因四问 → 根因修复 → 回归 → 独立复核 |
| 验收 | 任何准备说“完成”的时刻 | 任务卡 → 取证 → 判级 → 攻防 → 落账 |
| 发布 | 一批改动要对外交付 | 版本号 → 更新日志 → 发布前检查 → 回滚点 |

四种模式不是四套流程，而是同一套验收骨架的四个入口；起点不同，终点相同——都落到同一份验收账本。

## 3. 为什么验收是主轴

- **共同终点**：新功能没有验收项就不算做完；修缺陷没有回归证据就不算修好；发布没有验收账本就不许出。
- **只认证据**：A 是独立、可复算的读数，B 是现场观察，C 是推断；判通过要有 A 级读数，或两类不同的 B 级观察互证；C 只能提出假设。
- **四状态与三包结论**：v1 默认模板的单项状态为通过 / 未交付-失败 / 未交付-阻塞 / 未覆盖，包结论为通过 / 未交付（失败）/ 未交付（阻塞）；检查器默认拒绝“带欠账/带欠账交付”，读取历史账本时用 `--compat-debt` 显式放行；`--strict` 仍可叠加卡口。旧八列保留通过 / 未通过 / 阻塞。没有“基本可用”“通过（含残余）”这类模糊档；失败优先于阻塞，阻塞优先于通过。
- **单一状态源**：一次交付只有一份验收账本，其他文档只引用、不复制。
- **可反向检验**：每条“通过”先问“什么观察会推翻它”，每个门禁都用坏样本证明它会报红。

验收不是流程的最后一步，而是贯穿全程的判据。没有验收，前三种模式只是“做了”，不是“做成了”。

## 4. 哪些东西永远不进仓库

- **具体项目的内部资料**：项目文件名、模块名、目录结构、界面文案、需求原文。
- **设备适配层**：真机或模拟器型号、设备操作命令、签名证书、应用包名、设备截图、设备性能读数。
- **凭据与内部地址**：密码、令牌、Cookie、私钥、内网域名与 IP。
- **真实用户数据**：用户内容、个人信息、未脱敏的截图与日志。
- **与技能包无关的交付物**：比赛提交包、客户材料、演示视频母版。
- **本机环境产物**：虚拟环境、依赖缓存、IDE 配置、运行日志、临时文件。

判断标准只有一条：**换个项目、换台机器还能用吗？** 不能，就不进仓库。项目专属的适配材料放在仓库之外的本地私有目录，由 `.gitignore` 兜底。

## 5. 边界

不承诺全自动验收，也不替代人做发布决策；不绑定语言、框架和平台；自验收通过之前，仓库保持私有。
