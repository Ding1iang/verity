# 外部工作流对比与优化清单

> 记录日期：2026-11-07（Asia/Shanghai）；复核与实测：2026-11-08
> 性质：**分析记录，不是 verity 的规则正文**。本文件不改变 `SKILL.md`、`references/`、`templates/`、`scripts/` 的任何行为；引用本文件时，以 verity 现行规则为准。
> 对象：B 站视频 BV1kTnr63EKa、Matt Pocock/Skills 仓库、GitHub 上同类项目、verity v1.2.0。
> 一句话结论：Matt 管“怎么把事做对”，verity 管“凭什么说做完了”；两者不是替代关系，最佳组合是 Matt 上游 + verity 下游。
> 本次复核结论：verity 的骨架是对的；当前最该修的不是再加规则，而是把已经写下的规则接进检查器，尤其是用户旅程和完成审计。

### 2.1 视频与仓库正文的两处差异

- 视频说“每张 ticket 执行完 → code review → 提 PR → 关闭 ticket → 清理 worktree”；仓库正文 `implement-spec` 的主流程是：每票由 implementer 子代理完成并合回 integration branch，全部票完成后统一跑一次 code review，再由 tracker 的方式关票。精确行为以仓库当前正文为准。
- 视频说“垂直拆分或水平拆分”；仓库正文更严格：默认垂直 tracer bullet，只有大面积重构才用 expand–contract。

### 2.2 对 Matt 的整体评价

优点：

- 流程按上下文余量伸缩，不强迫所有任务走重流程。
- 共识和规格外化成文件，换会话不失忆。
- 票是任务图，blocking edges 决定并行 frontier；worktree 隔离冲突。
- 技能小而可组合，不拥有流程；SCOPE 要求技能来自真实会话里观察到的失败。
- 写作原则具体：描述决定触发、信息分层、每步有完成标准、用 leading words 压缩概念。

局限：

- 验收层只有原则和检查表，没有证据分级、单一账本、阻塞举证单。
- 依赖代理自律；没有模型外的完成闸门。
- setup 依赖 issue tracker 和标签，对小项目偏重；39 个技能对新手是负担。
- 演示是单条顺利路径；并行度、成本、质量没有基线。

## 4. verity 当前强项与缺口

### 4.1 不要动的骨架

- A/B/C 证据分级：A 独立可复算，B 现场观察，C 推断自述。
- 单一账本：一次交付只有一份 07，其他文档只引用不复制。
- F1–F6 六类假结论：以偏概全、旧证据复用、未跑先断、未验写成通过、没试过写成阻塞、多口径。
- 阻塞举证单：环境、注入通道、判据、数据四维；能力类要有正对照；解锁条件一句话。
- 用户旅程卡：3–7 步连续路径，每步可见变化与跨区域不变量。
- 10 类反例：假截图、假路径、旧证据、空账本、无证据通过、只跑主路径、门禁替代探针、设备未验写通过、重复状态源、旧结论词。

这些是 verity 比 Matt 和大多数 GitHub 同类更深的地方。借外部经验时，不要用“检查表 + PR 模板”替换它们。

### 4.2 主要缺口

1. **入口太晚**：从任务卡开始，不管任务卡之前的需求理解是否正确。
2. **覆盖校验不够**：检查器查账本行，但不保证任务卡每条 AC、旅程每一步都有对应行。
3. **证据仍是文本**：A 级证据可以手写；检查器无法分辨“真跑”与“写了一个读数”。
4. **证据与产物绑定不够**：有 commit，但没有构建物哈希、环境身份、截图 viewport。
5. **旧证据失效不彻底**：只查日期，不查取证后代码是否又改了。
6. **复核可以是同一个人**：v1 账本不要求每行复核人，批次信息里的“执行者/复核者”缺失只给 warning，不阻断；legacy 路径也只检查复核人非空，不校验两者是否同一人、是否独立会话。同一人写两遍也能过。
7. **没有完成线闸门**：检查器是建议，不是 commit/push/发布必须通过的闸门。
8. **没有快慢车道**：所有任务都走五步，代理容易形式化或绕过。
9. **规则维护没有闭环**：反例清单存在，但每批实际发生哪类假结论、下一版加什么检查，没有固定记录。

### 4.3 本次实测：规则已经承诺，门禁没有兑现

这不是“设计不够”，是当前版本可复现的正确性缺陷。以下都在 2026-11-08 用仓库现有脚本跑过，临时目录测试，不改变仓库。

1. **旅程失败仍判通过**。复制 `examples/04-project-v1`，在 07 中加入 `## 用户旅程`，写 `结论：未通过`，再跑 `check_evidence.py`，输出仍是 `[OK] ... 结论=通过`，rc=0。原因：`check_v1_ledger` 的必需段只有“包结论、外部证据登记、单项验收、欠账、阻塞举证”，不含“用户旅程”；`expected_v1_conclusion` 只看单项状态，不看旅程结论。
2. **完成审计缺失仍判通过**。`examples/04-project-v1/07-验收回归清单.md` 没有“完成审计”段，检查器仍判通过；`examples/05-release/07-验收回归清单.md` 也没有“用户旅程”段，同样通过。两份都是 README 让新用户先跑通的样板，等于在示范违规。
3. **初始化不生成旅程卡，模板却预填通过**。`templates/07-acceptance.md` 本身就把 `交付结论` 和 `旅程结论` 预填成“通过”；`scripts/verity.py init` 只生成 `task-card.md`、`07-验收回归清单.md`、`blocking-form.md` 和 `evidence/`，不生成 `journey-01.md`，却把模板原样复制过去。代理只要不细心，就会把“没做”写成“通过”。
4. **AC 到 07 没有映射**。任务卡 AC 表有 AC-ID，07 十列没有 AC-ID 或 `covers` 列，检查器也不比对；任务卡的 AC 可以一条都没落账，账本仍然通过。
5. **复核者独立性没有校验**。v1 账本不要求每行复核人；批次信息里的“执行者/复核者”缺失只给 warning，不阻断。legacy 路径也只检查复核人非空，不解析两者关系；同一人写两遍也能过。这使“独立复核”退化成一句自述。
6. **规则文本和模板互相矛盾**。`references/acceptance.md:96` 写“v1 十列账本（十列，含完成审计）”，但实际十列不含完成审计，完成审计是 07 的独立段；示例 04 也没有该段。模板、规则、示例三处不一致，代理按哪份做都能找到“依据”。同类漂移还有：`SKILL.md` 和 `README.md` 的标题写“三条硬规则”，正文实际四条；README 说“五份模板”，`templates/` 实际有 6 个文件。
7. **失败证据可以是“见截图”而没有图**。把示例 04 改成 `证据类型=截图`、`证据=见截图`、`状态=未交付-失败`，检查器仍输出 `[OK] ... 结论=未交付（失败）`，rc=0。v1 分支里截图校验只对 `通过/带欠账` 生效，`未交付-失败` 和 `未交付-阻塞` 不检查截图是否可读；legacy 分支用的又是 `通过/未通过/阻塞` 这套旧状态。两套状态口径并存，失败/阻塞的截图证据都能用一句“见截图”顶过去。这给“假失败”留了口子，和“证据仍是文本”是同一根。

### 4.4 历史证据：这些缺口不是推演

- notes-hap 工作区 250 个 session 中，59 个是有用户亲自发消息的主会话、863 条用户消息（2026-10-19 至 11-08；191 个 subagent session 已排除）。其中 7 个主会话做了关键段落抽取，其余做元数据与关键词扫描。扫描是文本匹配，不等于逐条语义判读。
- 32 条消息出现“阻塞”，21 条出现“说人话”，10 条出现“看不懂”，8 条出现“通过（含残余）”，4 条出现“带欠账”；2026-11-05 之后的 202 条消息里，仍有 12 条“阻塞”、6 条“说人话”、6 条“通过（含残余）”、4 条“带欠账”。
- 5 次版本级阻塞没有一次是功能坏了：G6 催后 6 分钟用 root + `hdc smode` 解决，G7 20 分钟后换 Chrome 跑真实产物拿到 320/380/900 三档，G2 是用户明确放弃。根因不是“没法验”，是把“这台模拟器造不出”当成了“没法验”。
- 2026-11-07 全量测试 49 项 = 45 通过/3 失败/1 未覆盖；随后用户指出设置页四个功能挤同一页、三个点菜单失效、日历点不动、左栏不能滚、中间列无选中、标签页满提示不合理等 6 类明显问题。用户原话：“说人话，告诉我为什么查不出来这种明显的使用问题？”
- 2026-11-06 用户原话：“补 验收层目前还比较薄弱，太像程序化验收，非常本不够完善成熟”“到底啥意思，说人话”“说人话，我看不懂”。
- 2026-11-07 用户原话：“总是有东西带出来，有东西没做。有些明明能解决……为什么不直接解决掉？还要带一嘴，让我再来提醒你做吗？”
- 这些不是抽象需求，直接对应 #14 旅程、#15 阻塞、#18 夹具、#29 自验收、#30 通道预检、#31 人话汇报。

## 5. 优化与借鉴清单（32 项）

> 下面不分先后，按问题域归类；每项都判断“对不对、值不值得、效果、代价”。这里的“值得”是相对 verity 的目标而言，不是排期建议。

### A. 流程与目标

#### 1. 快慢车道与风险分级

- 借：Matt 的上下文判断；ADD 的按影响调节。
- 判断：对，值得改。效果高，代价中。
- 做法：两维分流——复杂度（单点/跨模块）× 风险（可逆/不可逆、是否碰数据和安全）。低低走轻验收：一张任务卡、一条 A 级证据、一个独立复核人；其余走全流程。发布、数据与安全、跨模块、多步用户路径、无法复现的缺陷写成硬触发，不靠代理自判。
- 防住：所有任务都五步导致的仪式疲劳和形式化。
- 代价：可能误分类；硬触发兜底，轻验收也要独立复核。

#### 2. 立卡前 grill

- 借：Matt 的 grill-with-docs。
- 判断：对，值得改。效果高，代价中。
- 做法：五到十个带推荐答案的问题，只问会改变判据的：目标和不做什么、用户路径和跨区域不变量、失败与回滚。事实让代理查，决定让用户拍，答案写进任务卡。
- 防住：证据证明了一个理解错的目标；F1 的上游版本。
- 代价：一轮问答；模糊需求可能问很多，限制题量，先让用户自己捋一遍。

#### 3. 一页规格与决策记录

- 借：Matt 的 to-spec，但只取一页。
- 判断：只对一半，值得做轻量版。效果中高，代价中。
- 做法：spec-lite：问题、用户、目标、范围外、关键决定、验收方向；放任务卡链接里，不复制。小任务跳过。
- 防住：大功能只有任务卡，缺问题、用户、范围外、关键决定。
- 代价：两份文档；用链接而不是复制，避免第二状态源。

### B. 判据与覆盖

#### 4. 判据可判性 lint

- 借：goal-setter 的“只写会改变判断的条款”。
- 判断：对，值得改。效果高，代价低。
- 做法：每条判据必须有动作、可观察结果、阈值或二元判定；全称结论必须写样本范围；拦截“正常、流畅、友好、尽量、适当、等”这类词。允许人工豁免并记录理由。
- 防住：判据看起来像判据，实际无法判真假；F4。
- 代价：可能误报；豁免要留痕。

#### 5. AC、旅程、账本三向映射

- 借：proof-loop 的冻结 AC；agent-audits 的 criteria/evidence 对应。
- 判断：对，值得改。效果最高，代价中。
- 做法：给 AC 和旅程步骤稳定 ID（AC-01、J-01）；07 增加 covers 列；检查器要求每条 AC 至少一行或“不适用加理由”，每步旅程至少一行。
- 现状：07 十列没有 AC-ID 或 covers；任务卡 AC 表有 AC-ID，但检查器不比对；实测示例 04/05 的 AC 与 07 行无法逐条对上。
- 防住：F1 以偏概全的结构性入口；漏项无法被机器发现。
- 代价：模板加列、旧账本迁移；用 schema version 解决。

### C. 范围与证据

#### 6. 范围锁与工作区干净

- 借：cogpin 的 scope_lock；notes-hap 的 inScope/outOfScope。
- 判断：对，值得改。效果高，代价中。
- 做法：任务卡列 in-scope/out-of-scope 路径；检查器比对 changed files 和 untracked files；未声明文件要 scope_exception。
- 防住：范围漂移、顺手改坏、夹带无关改动。
- 代价：跨模块改动要维护路径；例外要写理由。

#### 7. 证据命令执行

- 借：ritalin 的 proof command；haechi 的 setup 预检；agent-audits 的 artifact capture。
- 判断：对，值得改。效果最高，代价最高。
- 做法：适配层加 evidence_commands 白名单；check_evidence --run 在干净 worktree 执行；捕获退出码、标准输出/错误、时间、git SHA；账本引用 EV ID。
- 防住：F3 未跑先断、F4 未验写成通过；把自述变成环境产物。
- 代价：安全、超时、环境依赖；命令必须白名单、无 shell 注入、可超时。

#### 8. 产物与环境身份

- 借：agent-audits 的 SHA-256、字节数、MIME；verity 的版本锚点。
- 判断：对，值得改。效果高，代价中高。
- 做法：artifact_sha256、build_id、env、viewport、timestamp 结构化；截图附 viewport 和哈希；构建物附 SHA-256。
- 防住：旧截图、旧构建、不同环境冒充当前证据；F2。
- 代价：采集麻烦；让适配层脚本自动填。

#### 9. 旧证据失效

- 借：ritalin 的 workspace hash；skillgate 的 base 检查。
- 判断：对，值得改。效果高，代价低。
- 做法：记录取证时的 workspace_hash/current diff；取证后工作区变了，证据自动失效；任务卡改判据立即作废（已有规则，但检查器不查）。
- 防住：F2 旧证据复用。
- 代价：取证后不能随便改代码；这正是想要的效果。

### D. 复核与强制力

#### 10. 独立复核强制

- 借：proof-loop 的 fresh verifier；verity 自己的执行者/复核者字段。
- 判断：对，值得改。效果高，代价中。
- 做法：producer 不等于 reviewer；高风险要求 reviewer 是新会话/独立代理；reviewer 对每条 AC 写 supports/does-not-support/unclear，并至少复跑一条 A 级命令。
- 防住：复核变成签名；自己给自己放行。
- 代价：多一个代理/会话；小任务可由用户复核。

#### 11. 完成线闸门

- 借：skillgate；ritalin 的 stop hook。
- 判断：对，值得改。效果高，代价中。
- 做法：verity gate 命令；pre-push/CI 失败即阻断；发布用服务端/CI，不依赖本地 hook。
- 防住：代理跑完检查器再忽略错误；提示词约束默认 0% 合规的问题。
- 代价：接入成本；本地 hook 可绕过，CI 才是硬边界。

#### 12. 防绕过

- 借：cogpin。
- 判断：对，值得改。效果高，代价中高。
- 做法：策略从 base commit 读；保护 .verity 和测试文件；禁止删除断言/跳过测试、--no-verify；覆盖率阈值只升。
- 防住：改检查器、删测试、加 skip、改 adapter 降低门槛。
- 代价：规则复杂；只对高风险/团队仓库开，个人项目可关。

### E. 账本、旅程与发布

#### 13. 完成审计结构化

- 判断：对，值得改。效果中高，代价低。

#### 14. 旅程卡强制与负路径

#### 17. 复盘与 F 类统计

### F. 规则维护与写作

#### 18. 红队夹具

#### 19. 技能写作

#### 20. 术语表与判级校准

#### 21. 版本迁移与 schema

- 防住：模板演进后旧账本不兼容。

#### 22. 适配层预检

#### 30. 取证通道正对照预检

- 借：用户历史里的真实反馈，不是外部项目。
- 判断：对，值得改。效果高，代价低。
- 做法：收口输出固定两层。第一层最多三行：结论、用户会看到什么变化/什么没做到、下一步；不出现 ID、A/B/C、账本路径、F 编号。第二层才是现有 `结论/账本/旅程/证据/卡点` 代码块。两层都从同一份 07 生成，不新增第二套口径。
- 防住：规则越严越没人读；用户被迫问“说人话/欠账是啥”；技术正确但沟通失败。
- 代价：模板多三行；需要检查器禁止第一层出现术语/编号。

#### 32. 证据包自包含

- 借：2026-11-08 通宵 V1.2 收尾的实测（86 个复验文件未入库、11 条证据路径不存在）。
- 判断：对，值得改。效果高，代价低中。
- 做法：批次目录生成 `manifest.json`，每条证据记录相对于项目根的路径、`git ls-files` 是否已跟踪、SHA-256、字节数；交付前用干净检出复跑一次；被 `.gitignore` 的证据日志要么 force-add，要么移到盘点目录之外。manifest 不通过，批次不能判通过。
- 防住：证据只在作者机器上存在；账本写“见截图”但交付包里没有图；旧构建截图混入新批次。
- 代价：多一个生成/核对步骤；对二进制大文件要有体积上限。

## 6. 不抄清单

下面这些在 Matt 或同类项目里成立，但不适合直接搬进 verity：

| 不抄的东西 | 为什么不抄 |
|---|---|
| 39 个技能全套 | verity 是一个验收协议，不是技能超市；加更多技能会稀释入口 |
| 强制 issue tracker 和标签 | verity 的适配层可以指向项目现有工具；不强迫 GitHub/GitLab |
| 每个任务都写完整七节规格 | 只有大功能/多会话需要；小任务用 spec-lite 或直接任务卡 |
| 每个任务都开 worktree、多代理 | 只有可并行的票值得；否则增加成本、冲突和清理负担 |
| Matt 的 PR Summary 模板整套 | verity 的 07 才是状态源；PR 摘要应由 07 生成，不是新格式 |
| zero-knowledge、FHE、服务端证明 | 个人和小团队用 CI 就够；复杂度和运维成本不成比例 |
| proof-loop 的 JSON-only 门禁 | 它只查结构，不核对 AC 覆盖和证据真假；比 verity 现有检查器弱 |
| ADD 的新 AC.md | verity 的单一 07 更好；再建一个权威来源会制造第二口径 |
| goal-setter 做成独立技能 | “只写会改变判断的条款”是写法，不是产品；不需要新入口 |
| rebar 的完整 ticket store | 除非真的要做多 agent 调度；否则是范围膨胀 |
| persona-harness 的 Java/Spring 绑定 | verity 要语言无关；只借它的伪造证据 fixture 思路 |
| teach、prototype、code review 的代码坏味道清单 | 它们解决实现质量和教学，不是交付验收；塞进来会让 verity 失焦 |
