# 示例五：发布——v1.0.0 对外检查

> “发布模式”的完整样例：先有通过的验收账本，再做版本、更新日志、回滚点、干净构建和发布后冒烟检查。示例里的版本号、hash 和读数为演示数据，真实发布必须换成自己的记录。

## 输入

发布候选：示例项目 `1.0.0`，范围只有“按标签过滤条目”一项新能力，没有不兼容改动。

发布前必须先回答：

1. 验收账本是否已经收口为“通过”，且没有待验、验中、未通过或阻塞项？
2. 版本文件、标签、更新日志标题是否都指向同一个版本号？
3. 发布产物能否从干净检出构建，hash 是否能和标签对应？
4. 上一可用版本、恢复步骤和回滚后的冒烟检查是否已经准备好？
5. 发布后按用户入口做一次冒烟，结果是否有记录？

## 任务卡

见 [`task-card.md`](task-card.md)（v2）。任务卡只定发布范围、版本锚点、车道和检查项；真正的验收结论在 07 账本里。

## 文件说明

| 文件 | 作用 |
|---|---|
| `README.md` | 发布输入、命令、预期输出和反例说明；同时作为本示例的日志证据 |
| `task-card.md` | 发布任务卡（范围、版本、车道、AC） |

| `07-验收回归清单.md` | 唯一状态源（发布前检查账本） |

## 如何复跑

在仓库根目录执行：

```bash
python3 scripts/check_evidence.py examples/05-release/07-验收回归清单.md
```

## 预期输出

```text
[OK] <仓库根>/examples/05-release/07-验收回归清单.md：5 行，结论=通过（通过 5）
```

退出码为 0。检查器只验证账本结构、证据身份和状态自洽；发布是否真的可以对外，仍由发布检查表和独立复核决定。

## 反例

门禁全绿不等于探针跑过。下面这个账本把“门禁全绿；没跑探针”写成通过证据，检查器必须报 `E_PROBE_MISSING`：

```bash
python3 scripts/check_evidence.py examples/05-release/bad-gate-only/07-验收回归清单.md
```

预期看到：

```text
[FAIL] .../bad-gate-only/07-验收回归清单.md:... [E_PROBE_MISSING] ... 只写了门禁全绿，但自述没跑探针；门禁不能替代探针结论
```

这个反例说明：检查器不会因为所有门禁命令退出 0 就放行；证据必须能回答对应验收项，不能用“全绿”替代“探针”。

## 这个例子演示了什么

- 发布模式先看 07 结论，再看版本、更新日志、构建产物和回滚点，顺序不能倒。
- 发布检查也写成验收项，每条都有证据，不靠一句“已经检查过”。
- 版本号、标签和更新日志标题必须三处一致；示例用 `v1.0.0` 演示。
- 回滚点必须在发布前准备，不能等出事再找上一版。
- 发布后冒烟是独立验收项，不能用“构建成功”代替。
- 发布批次必须写发布风险和复盘；回滚未演练时必须标“未验证”。
