# 示例四：验收——schema 2 账本

> “验收模式”的样例：任务卡先定靶，执行者只取证判级，不改代码；结论只从 07 账本读出。示例项目和读数均为演示数据。

## 输入

一个已经实现完成、等待验收的候选版本。验收者拿到任务卡后，只做三件事：

1. 按任务卡的验收项逐条取证，不扩大范围。
2. 把每条证据写进账本，证据必须能落到文件或命令读数。
3. 按账本状态收口，不凭印象写“通过”。

## 任务卡

见 [`task-card.md`](task-card.md)（v2）。示例只有一条验收项，用来演示 AC、旅程步骤、证据身份和完成审计如何互相对上。

## 文件说明

| 文件 | 作用 |
|---|---|
| `README.md` | 验收输入、命令、预期输出和反例说明；同时作为本示例的日志证据 |
| `task-card.md` | 验收任务卡（定靶、范围锁、AC） |
| `journey-01.md` | 用户旅程卡（3 步） |

## 如何复跑

在仓库根目录执行：

```bash
python3 scripts/check_evidence.py examples/04-project-v1/07-验收回归清单.md
```

`check_evidence.py` 本身不依赖适配层。但完整本地门禁还要执行 EV 命令并核对证据清单，必须显式指定测试适配层：

```bash
python3 scripts/verity.py gate --root . \
  --ledger examples/04-project-v1/07-验收回归清单.md \
  --adapter tests/fixtures/valid-adapter.json --run
```

预期 5/5 通过（证据账本、覆盖总表跳过、证据包清单、范围锁、脱敏）。不带 `--adapter` 时证据包清单步骤会跳过，只输出 4/5；4/5 不是完整门禁，不能引用为“通过”。

## 预期输出

```text
[OK] <仓库根>/examples/04-project-v1/07-验收回归清单.md：1 行，结论=通过（通过 1）
```

退出码为 0。这里的 0 只表示账本格式、证据身份与状态自洽，不表示业务验收真实通过；证据内容仍要由复核人核对。

## 反例

截图是证据类型，不是“写一句见截图”。下面这个账本把证据类型写成“截图”，证据只写“见截图”，没有图片路径：

```bash
python3 scripts/check_evidence.py examples/04-project-v1/bad-fake-screenshot/07-验收回归清单.md
```

预期看到 `E_SCREENSHOT`（同时仍会检查任务卡、旅程和完成审计等结构）：

```text
[FAIL] .../bad-fake-screenshot/07-验收回归清单.md:... [E_SCREENSHOT] ... 的证据类型是截图，但没有可读的截图文件
```

## 这个例子演示了什么

- 验收模式不改代码：证据来自执行者的实际观察和命令读数，不来自实现者的自述。
- 任务卡 AC 必须被账本“覆盖 AC”列逐条覆盖，旅程每一步都要有账本行映射。
- 本地证据要登记 SHA-256、字节数、构建号、环境、取证时间和 workspace_hash。
- 完成审计逐 AC 对账；独立复核逐 AC 给出 supports / does-not-support / unclear，并至少复跑一条 A 级命令。
- 截图、日志、布局树等证据类型各自有最低要求，写“见截图”不算交付。
