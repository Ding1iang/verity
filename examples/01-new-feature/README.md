# 示例一：新功能——按标签过滤书签

> 本目录是“填写完成的任务卡 + 验收账本”长什么样子的样例。示例项目、版本号和测试读数为演示数据；真实任务必须换成自己的实测记录。

## 输入

用户原话（需求单节选）：

> 书签一多就找不到了。希望能按标签过滤，比如只看工作相关的；没有匹配的时候别报错，告诉我没有就行。

拆成可验收的行为：

1. 指定一个存在的标签时，只列出该标签下的书签。
2. 指定不存在的标签时，输出明确的空结果提示，不报错。
3. 不指定标签时，输出与改动前完全一致。

## 任务卡

见 [`task-card.md`](task-card.md)（v1）。三条验收项分别覆盖主路径、空结果和默认行为。

## 文件说明

| 文件 | 作用 |
|---|---|
| `README.md` | 输入、预期输出和本说明 |
| `task-card.md` | 填写完成的任务卡（定靶） |

## 如何复跑

在仓库根目录执行：

```bash
python3 scripts/check_evidence.py examples/01-new-feature/07-验收回归清单.md
```

## 预期输出

```text
[OK] <仓库根>/examples/01-new-feature/07-验收回归清单.md：3 行，结论=通过（通过 3）
```

退出码为 0。如果出现任何 `[FAIL]` 开头的行，按提示修账本，不要修改检查器来迁就账本。

## 反例

只跑主路径却写成通过，是“证据边界小于验收项”的典型错误。下面这个账本故意只写“只跑了主路径”：

```bash
python3 scripts/check_evidence.py examples/01-new-feature/bad-main-path/07-验收回归清单.md
```

预期看到 `E_SCOPE_GAP`，而不是 `[OK]`：

```text
[FAIL] .../bad-main-path/07-验收回归清单.md:29 [E_SCOPE_GAP] ... 的证据自述只覆盖主路径，不能支撑整个验收项通过
检查失败：1 项错误，0 项警告
```

## 这个例子演示了什么

- 验收项写成“给定……应得到……”，每条都有最低证据和取证方式。
- 证据列写命令和读数，不写“测试通过”“功能正常”这类无法复核的话。
- 空结果也是一条验收项：有没有匹配都算用户能看到的行为。
- 默认行为单独列一条，防止新功能把旧路径改坏。
