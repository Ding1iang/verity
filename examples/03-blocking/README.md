# 示例三：阻塞——中文 PDF 导出缺字体

> 本目录是“阻塞怎么写、为什么不是通过”的样例。示例项目、版本号和读数为演示数据；真实任务必须换成自己的实测记录。

## 输入

需求单节选：

> 书签要能导出成 PDF，发给同事看。中文必须正常显示，不能是方框或空白。

## 任务卡

见 [`task-card.md`](task-card.md)（v1）。四条验收项中，中文导出是主目标，英文导出作为正对照，错误提示和数据外的更新日志各一条。

## 为什么结论是阻塞，不是通过

- 中文 PDF 没有生成成功：导出在写字体阶段失败，生成的文件缺少中文字形。
- 英文 PDF 用同一个库导出成功，说明“生成 PDF”的能力存在，缺的是运行环境里的中文字体资源，不是实现没写。
- 环境、注入通道、判据、数据四个维度都试过，结果一致（详见 [`blocking-form.md`](blocking-form.md)）。
- 解锁条件一句话能给出：提供一份允许嵌入的开源中文字体文件，放进约定目录后按固定命令复验。

阻塞不等于通过：账本结论写的是“阻塞”，在这一项解除之前，不允许对外说“可以发布”或“基本完成”。

## 如何复跑

在仓库根目录执行：

```bash
python3 scripts/check_evidence.py examples/03-blocking/07-验收回归清单.md
```

## 预期输出

```text
[OK] <仓库根>/examples/03-blocking/07-验收回归清单.md：4 行，结论=阻塞（通过 2 / 阻塞 1 / 不适用 1）
```

退出码为 0。注意：检查器退出码 0 只表示账本格式与状态自洽，不表示交付通过；这份账本的结论是阻塞。

## 这个例子演示了什么

- 阻塞是“外部条件缺失”，不是“没做完”或“不会做”；举证单必须四维齐全。
- 正对照证明能力存在：英文 PDF 能导出，所以问题不在 PDF 库本身。
- 阻塞项与“通过”“不适用”可以同表存在，但整体结论必须是阻塞。
- 解锁条件是一句话能给的，不需要执行者再做一轮猜测。
