# 新功能模式

> 从“想要”走到“可验收”。澄清不过不写规格，计划没定稿不开工。

## 0. 适用边界

用于给系统增加原本没有的能力，或改变已有功能的预期行为。

不用于：

- 已有行为与预期不符——走 `references/bug-fix.md`。
- 只做验收、不改代码——走 `references/acceptance.md`。
- 一批改动准备对外——走 `references/release.md`。

终点不是“代码写完”，而是 `07-验收回归清单.md` 收口为通过，且每条验收项都有达标证据。

## 1. 五个阶段

| 阶段 | 必须回答 | 产出 | 出口条件 |
|---|---|---|---|
| 需求澄清 | 谁在什么场景遇到什么问题，不做会怎样 | 需求说明或任务卡「目标」 | 目标可判真假，非目标明确，未决项有决策人 |
| 规格 | 用户能看到哪些行为，边界和失败路径是什么 | 验收项清单，写入任务卡 | 每条验收项都有判据、最低证据和取证方式 |
| 计划 | 分几步、每步改哪里、每步怎么验、提交怎么拆 | 实施计划，状态为「定稿」 | 计划评审通过并留下定稿记录 |
| 实现 | 当前提交只做哪一件事，对应哪些验收项 | 代码、测试、实施记录 | 每个提交可单独解释和回滚，测试同提交通过 |
| 验收 | 每条验收项的证据等级和结论是什么 | `07-验收回归清单.md`、更新日志 | 全部通过或不适用，没有待验、验中、待定 |

### 1.1 需求澄清

先把问题说清楚，不要先给方案。任务卡按 `templates/task-card.md` 写。逐条回答：

- 谁在什么场景遇到什么问题？
- 现在用什么办法绕过？代价是什么？
- 不做会怎样？为什么现在做？
- 成功后用户看到什么不同？
- 必须做什么？明确不做什么？
- 有哪些约束：兼容性、数据、权限、性能、平台？
- 哪些问题还没有答案？决策人是谁？

澄清阶段出现“用某个框架”“加一张表”“改某个接口”，先记到待定，回到问题本身。方案是下一阶段的事。

**出口检查**：目标能写成一句可判真假的话；非目标列得出来；影响范围的未决项都有决策人和期限。做不到就不进入规格。

### 1.2 规格

把需求改写成用户可观察的行为，不写实现。

每条验收项至少包含：

1. **ID**：后续账本、提交和复核都引用它。
2. **判据**：给定什么输入或操作，应得到什么可观察结果，否则不算过。
3. **最低证据**：A 级读数，或两条不同通道的 B 级观察；按 `references/evidence.md` 定级。
4. **取证方式**：具体命令、操作路径或检查方法。

规格要覆盖主路径、边界、空状态、错误路径、权限和兼容范围。只写快乐路径的规格，验收时一定漏。

规格里出现“正常”“稳定”“流畅”“符合预期”，退回重写：这些词无法判假。

### 1.3 计划

计划至少写清六件事：

1. 工作拆成几步，步骤之间的依赖顺序。
2. 每步动哪些文件、模块或配置。
3. 每条验收项由哪一步、用什么方式验证。
4. 提交怎么拆，每个提交只做哪一件事。
5. 风险、回滚方式和需要提前准备的环境或数据。
6. 执行者和复核者。

计划末尾必须有定稿记录：

```text
计划状态：定稿 v1
定稿时间：<时间>
评审人：<姓名或角色；自检写“自检”>
```

**没有这段记录，不写第一行代码。** “先写着看”“边做边想”不算计划。计划可以很短，但必须先定稿。

定稿的含义：范围、验收项、步骤、提交拆分和验证方式都已确定，没有会影响开工的待定项。计划变更时升版，写明哪些旧证据因此作废；口头改计划不算数。

### 1.4 实现

- 按计划顺序推进，不插队、不顺手扩展。
- 功能代码和对应测试同一次提交；测试没通过不算实现完成。
- 每个提交对应明确的验收项 ID，提交信息里写任务编号和 AC ID。
- 中大型需求写 `06-实施记录.md`：只写已经发生的改动、验证结果和存疑点，不写“打算怎么做”。
- 发现计划不可行，停下来改计划并升版，不静默偏离。
- 遇到外部条件缺失，按 `templates/blocking-form.md` 填举证单；不要用“差不多完成”掩盖。

### 1.5 验收

按 `templates/07-acceptance.md` 建账本，一项一行，逐条取证。关键项换独立通道复核；高风险项由非执行者复核。用户能感知的变化同时写更新日志，写法见 `references/release.md` 第 3 节。

验收阶段只认证据，不认“我觉得可以了”。任何一项没有达标证据，整体就不能写通过。

## 2. 一个提交只做一件事

**定义**：一个提交的 diff 只有一个目的，能用一句话说清，不需要“顺便”“同时”“另外”。

| 场景 | 拆法 |
|---|---|
| 新功能 + 顺手修一个文案错字 | 拆成两个提交 |
| 新功能 + 它的测试 | 同一个提交，测试是功能的一部分 |
| 重构 + 行为变化 | 先做行为不变的重构并跑全绿，再做行为变化 |
| 全仓格式化 + 一个修复 | 格式化单独提交，或不格式化无关文件 |
| 依赖升级 + 必要的适配代码 | 同一个提交；无关功能另拆 |

提交信息格式：

```text
feat: <用户能感知的结果>
task: <任务编号>；ac: <AC-1, AC-2>
```

提交前检查：

- `git diff --stat`：文件数和行数是否明显超出这件事。
- `git diff`：有没有计划外的文件、调试代码、配置或数据。
- `git show --stat <commit>`：事后能否只看一个提交就理解并回滚。

一个提交混了三件事，复核的人无法判断哪一行导致回归，回滚也会把无关改动一起带走。

## 3. 轻量通道

单点需求、一个会话能做完并验完时，可以合并文档，但不能跳过门：

| 文档 | 轻量需求 | 中大型需求 |
|---|---|---|
| 需求说明 | 并入任务卡「目标」 | 独立 `01-需求.md` |
| 规格 | 任务卡验收项 | 独立 `02-规格.md` |
| 计划 | 任务卡附页，标注「定稿 v1」 | 独立 `04-计划.md` |
| 实施记录 | 可省略，提交记录即过程 | `06-实施记录.md` |
| 验收账本 | 必须有 `07-验收回归清单.md` | 必须有 |

轻量不等于免检：验收项、最低证据、计划定稿、一个提交一件事，一个都不能少。

## 4. 常见失败

| 失败形态 | 后果 | 正确动作 |
|---|---|---|
| 先写代码，再补需求 | 验收项围着已实现的东西写，范围失控 | 停下来补澄清和验收项，再继续 |
| 计划只在脑子里 | 无法复核，也无法判断是否偏离 | 写一页计划，定稿后再开工 |
| 一个提交塞进多个目的 | 无法审查、无法单独回滚 | 按目的拆分提交 |
| 验收项写“功能正常” | 无法判假，最后只能靠感觉 | 改成“给定……应得到……” |
| 测试留到最后 | 返工，且容易把测试改成迁就实现 | 每条验收项在实现阶段就有验证 |
| 范围越做越大 | 交付延期，原有验收项被稀释 | 新需求另立任务卡，不塞进当前范围 |

## 5. 收口自检

- [ ] 目标能用一句话判真假，非目标已写。
- [ ] 每条验收项都有判据、最低证据和取证方式。
- [ ] 计划有「定稿」记录，且没有影响开工的待定项。
- [ ] 每个提交只做一件事，功能和测试同提交。
- [ ] 每条验收项在 07 里有且只有一行，证据可定位。
- [ ] 高风险项已独立复核，复核人不是执行者。
- [ ] 用户可感知的变化已写进更新日志，且没有内部术语。
- [ ] 临时脚本、日志和测试数据已清理。
