# 验收规则

> 任务卡定靶，07 记账，按模板收口。本文件是判定与落账的唯一规则。v1 默认模板（schema 2）用四状态、三包结论和十三列账本；检查器默认四状态三结论并拒绝带欠账/带欠账交付，读取历史账本时用 `--compat-debt` 显式放行，`--strict` 仍可叠加卡口；旧八列仍用七状态和三态，两种格式不要混写。
>
> 执行层面的操作与观察见 `references/acceptance-run.md`；本文件只定义任务卡、状态和落账规则。

## 1. 任务卡字段

任务卡在动工前写，模板见 `templates/task-card.md`。

| 字段 | 必填 | 写什么 | 不合格示例 |
|---|---|---|---|
| 任务编号 | 是 | 稳定 ID，账本、提交和对话都引用它 | “这次的任务” |
| 任务卡版本 | 是 | v1、v2……判据或范围一改就升版 | 改了不记 |
| 目标 | 是 | 一句话，能判真假 | “优化体验” |
| 范围（做） | 是 | 本次要动的功能、文件、环境 | “相关模块” |
| 范围（不做） | 是 | 明确排除项，防止扩边 | 空着 |
| 验收项 | 是 | 每条含 ID、判据、最低证据、取证方式 | “功能正常” |
| 约束与红线 | 是 | 不能破坏的既有能力、不能碰的数据 | 空着 |
| 交付物 | 是 | 文件或产物清单，可逐项核对 | “代码” |
| 版本锚点 | 是 | 基线 commit、构建号、环境指纹 | “最新版” |
| 执行者与复核者 | 是 | 两个角色，必须不同人；每行产出者与复核者也不得相同 | 全写自检，或自称独立复核 |
| 车道与风险 | 是 | 轻验收或全流程，并写明是否触发跨模块/不可逆/数据/安全/发布硬触发 | 只写“按流程走” |
| 立卡前盘问 | 全流程必填 | 5–10 条追问、推荐答案和用户决定 | 空表或只写“已确认” |
| 规格摘要（spec-lite） | 全流程必填 | 一页内的目标、不做、关键决策和验收边界 | 写成七节规格书 |
| 范围锁 | 是 | “做/不做”的文件或目录路径，门禁按它检查越界 | 只写模块名 |

**判据写法**：给定 <输入或操作>，应得到 <可观察结果>，否则不算过。禁止“正常”“稳定”“流畅”“符合预期”这类无法判假的词。

**任务卡变更**：判据、范围、版本锚点任一改动都要升版，并在变更记录里写明哪些旧证据因此作废。口头改判不算数。

### 1.1 用户旅程（批次前置）

每个批次、每次交付至少一份用户旅程卡；跨区域或多步骤改动至少三份。模板见 `templates/journey-card.md`，规则见 `references/journey-acceptance.md`。

- 旅程卡写用户从入口到目标的 3–7 步连续路径，每步同时写“可见变化”和“跨区域不变量”。
- 07 的“用户路径”列必须写清旅程 ID 和步骤，例如 `J-01 / 步骤 2`；不能只写“打开页面”。
- 没有旅程卡，批次最多记“未覆盖”，不能判通过。
- 旅程卡结论为通过、未通过、阻塞或未覆盖；它不替代 07 的单项状态。批次通过 = 07 全部通过或不适用 + 至少一份旅程卡通过 + 没有未解决的跨区域不变量。
- 纯 API、CLI、数据迁移等没有界面的任务可以写“不适用”，但必须写理由和替代路径。

## 2. 七种状态（旧八列）

账本里每个验收项在同一时刻只能有一个状态。

| 状态 | 含义 | 进入条件 | 谁能写 |
|---|---|---|---|
| 待验 | 还没开始取证 | 任务卡已立 | 执行者 |
| 验中 | 正在取证，尚无结论 | 已有取证记录 | 执行者 |
| 通过 | 达到该项最低证据等级，覆盖声明范围 | 证据行完整、可定位，并按任务卡完成复核 | 执行者取证，复核人复核（可自检） |
| 未通过 | 有证据表明不达标，或证据不足、已失效 | 有反证或缺口说明 | 执行者或复核者 |
| 阻塞 | 外部条件缺失，不是实现问题 | 举证单四维齐全、有正对照、有解锁条件 | 执行者提交，复核者确认 |
| 不适用 | 该项对本次交付不成立 | 写明理由并经任务卡作者批准 | 任务卡作者 |
| 待定 | 判据本身没定，无法验收 | 记录待决问题和决策人 | 任务卡作者 |

**优先级：未通过 > 阻塞 > 通过。** 任何一项未通过，整体不得写通过；阻塞项没有举证单的，按未通过记。

待验、验中、待定都不算通过。收口时，与阻塞项无关的这类状态按未通过记；因某个阻塞项直接导致无法开始的项，在账本标注依赖的阻塞 ID，随该阻塞项一起收口。

## 3. 三态交付（旧八列）

整体结论只允许三个：

| 结论 | 条件 | 允许的措辞 |
|---|---|---|
| 通过 | 所有验收项均为通过或不适用，至少一份用户旅程卡通过，且没有未解决的跨区域不变量 | “通过” |
| 未通过 | 任一项未通过、证据不足或失效，仍有未取证项，或旅程卡未通过/缺失 | “未通过”，附欠账表 |
| 阻塞 | 没有未通过项；至少一个阻塞项且举证单齐全；其余未完成项都能追溯到该阻塞项 | “阻塞”，附举证单 |

欠账不是第四态。欠账就写“未通过”加欠账表：缺什么、谁补、何时补。阻塞和未通过同时存在时，写未通过。

## 4. 阻塞举证单

写“阻塞”之前必须按 `templates/blocking-form.md` 填单。缺任意一项都不算阻塞，按未通过记。

**硬门槛**：

1. **四个维度各至少试过一次**：环境（换设备、浏览器或实例）、注入通道（换工具或替身）、判据（换读数来源：界面到库、日志或像素）、数据（换夹具或故障注入）。
2. **能力类结论必须有正对照**：先在已知可用的地方证明这个能力存在。正对照通过，说明是目标或方法的问题，不是能力缺失；正对照也失败，阻塞才成立。
3. **解锁条件要一句话能给出**：需要谁提供什么，拿到后怎么复验。
4. **影响面写清**：哪些验收项被连带阻塞。
5. **任一维度没试，阻塞就不成立**：过程中记待验，收口时按未通过记，不许写阻塞。

举证单复核不通过时，阻塞降为未通过，并把差的那个维度写进欠账表。

## 5. 07 单一状态源

07 是本次交付的唯一状态源，状态只认这一份账本。

- 文件名固定为 `07-验收回归清单.md`，一次交付一份，批次名写进标题。
- **一个批次就是一本账，不按模块拆。** 批次跨多个模块（例如同时改加密和导入导出）时，仍只建一本 07：在“批次信息”里把涉及的模块和批次目录都写上，在“单项验收”里用验收项 ID 前缀区分模块（如 `ENC-01`、`IMP-01`）。⛔ 不要为了对齐模块在同一个批次目录里建第二本 07——那会让同一批的证据被拆成两套口径。
- 一个验收项恰好一行。一行必须能独立读懂：ID、验收项、判据、最低证据、证据等级、证据文件或命令读数、状态、复核人。
- 独立复核的“复跑命令”只填 EV ID，检查器从 `evidence/ev-runs.log` 读取实际执行记录并重算输出哈希；任意 shell 命令、伪造输出或旧 HEAD 记录都不能作为复核依据。
- v1 的“用户路径”列写 `J-xx / 步骤 n`，与 `journey-xx.md` 对齐；没有旅程 ID 的行只能算单点检查，不支撑批次通过。
- 证据列优先写证据文件的相对路径；没有落盘文件时写完整命令加读数。路径必须指向仓库内或交付物内的真实文件，不许写不存在的占位路径。
- 一个验收项有多条证据时，用分号在同一行并列，仍只占一行；不许拆成多行或写成“同上”。
- 其他文档、提交信息和对话只能引用账本的行或 ID，不得复制状态表。发现两处不一致，以账本为准，并记一次 F6（多口径）。
- 状态变更必须有依据：待验到验中记录取证动作，进入通过、未通过或阻塞必须指向证据 ID 或举证单。每次变更在“变更记录”追加一行：时间、ID、旧状态到新状态、依据 ID、操作人。
- 收口后账本归档，不覆盖历史批次；后续批次新建文件并引用旧批次。
- **范围锁与证据路径一律写“项目根相对”路径。** 项目在 git 仓库的子目录里（monorepo，例如仓库根是 `monorepo/`、项目根是 `monorepo/app/`）时，检查器会先把 `git status`/`git diff` 给的仓库根相对路径剥掉项目前缀再比对；任务卡和 07 里不要写带仓库目录名的路径（如 `app/src/...`），否则会判成“改动未声明”。
- 一行写不下，说明这不是一个验收项，拆成两项；不许把多个结论塞进一行。
- 八列是最小集。项目需要时可在八列之后追加“用户路径”“产出者”“置信度”“时间”“commit”等扩展列；扩展列不得替代八列，状态列仍只有一个。v1 的“用户路径”不是说明文字，必须能回到一张旅程卡的具体步骤。
- v1 默认模板已切到 schema 2 十三列：验收项 ID、覆盖 AC、用户路径、预期、证据类型、证据、证据等级、产出者、复核者、置信度、时间、commit、状态。v1 账本还必须有批次信息、用户旅程、包结论、外部证据登记、单项验收、证据身份、完成审计、独立复核、欠账、阻塞举证十段；发布批次另需复盘与发布风险。项目在适配层 `paths.ledger_template` 指向自己的模板后，`init` 按项目模板生成，`check_evidence.py --adapter` 按模板 marker 识别。旧八列账本仍可读，用 `--format legacy`。两种格式不要混写。旧十列可用 `python3 scripts/verity.py upgrade <07 文件>` 补列和空段，迁移后仍需人工补证据与复核；旧八列缺少覆盖 AC、证据身份和完成审计，`upgrade` 会明确拒绝并提示新建 schema 2 批次，不会生成看似合规的空壳。
- 仓库外证据：在证据列写外部件 ID，并在 07 的“外部证据登记”登记位置、产出者、获取方式、校验值、保留期限；没有登记按 C 级处理。

**证据自述缺口**（v1 schema 2）：证据列自述里承认“只跑了主路径”“门禁全绿但没跑探针”“设备未验”时，状态不能写“通过/带欠账”。检查器分别报 `E_SCOPE_GAP`、`E_PROBE_MISSING`、`E_DEVICE_UNVERIFIED`；这不是文字游戏，而是证据边界小于验收项边界。截图类型必须能解析出一张真实、非空的图片文件，只有“见截图”几个字会报 `E_SCREENSHOT`。

### 5.1 通过时账本必须内部一致（1.3.2）

包结论写“通过”之前，下面几条必须同时成立；任何一条不成立都由检查器直接报错，不能靠人工“看一遍”放行：

| 错误码 | 触发条件 | 说明 |
|---|---|---|
| `E_DEBT_IN_PASS` | `## 欠账` 仍有任何未闭合描述 | 通过账本的欠账段只能为空或写“无/无欠账”；写“唯一未闭合项”“仍欠”“待补”都算未通过 |
| `E_BLOCKING_IN_PASS` | `## 阻塞举证` 仍有当前阻塞描述，或 `blocking-form.md` 当前状态不是 closed | 只要阻塞单存在就解析它的当前状态，不再依赖是否存在“未交付-阻塞”行；历史结论必须收进“历史记录”小节，当前状态只能有 open / closed 一个值 |
| `E_REVIEW_MISMATCH` | 同一 AC 有重复复核行；复核人等于该 AC 产出者；复核命令不是 EV ID；EV 未登记该 AC；执行记录缺 `ac_id`/`ac_ids` 或与复核 AC 不对应 | 每个 AC 只能有一行 supports；一个 EV 只能给它注册的 AC 背书，例如搜索主流程的 EV-03 不能给 Ctrl+F 的 AC-04 签字 |
| `E_ARTIFACT_STALE` | 证据记录的 HAP SHA-256 或被测 commit 不是 07 批次信息的最终值 | 旧 HAP、旧 commit、旧构建截图一律失败；执行记录还必须带 `hap_sha` |
| `E_AUDIT_CONTRADICTION` | 状态“通过”的 AC，其完成审计读数含“失败/未进入/未验证/未通过/阻塞/不成立”等相反描述 | 完成审计必须写最终证据的成功读数；修好前的失败描述不能留在通过行里 |
| `E_COMPLETION_MISSING` | 任务卡的某个 AC 没有同时出现在单项验收和完成审计 | 通过账本必须逐 AC 对得上，不能只覆盖一部分 |
| `E_READING_MISSING` | 状态“通过”的行，读数为空或只有“正常/通过/无异常/ok”这类无信息词 | 读数必须带数字、px/vp/ms/%、`exit=`、`sha256`、`color=` 或 DB 字段；失败/阻塞行允许写卡点 |

这六条是“通过”的硬门槛，不是建议。`--run` 生成的每条 `ev-runs.log` 记录现在都带 `ac_id`、`ac_ids` 和 `hap_sha`；复核表填的 EV 必须能在日志里找到对应 AC 和最终 HAP 的记录。

## 6. 禁止“通过（含残余）”与把欠账当通过

这两种写法是把未通过伪装成通过，直接判为口径违规。

| 错误写法 | 为什么不行 | 正确写法 |
|---|---|---|
| 通过（含残余：窄窗口未验） | 未验项被并进通过 | 未通过，欠账表写“窄窗口布局未验，需补证” |
| 带欠账交付 | 在项目合同禁止欠账时，它把未通过伪装成通过 | 未通过，附欠账表；或阻塞，附举证单；默认即卡住；历史账本用 `--compat-debt` 显式读取 |
| 基本可用 | 无法判真假 | 按账本写通过或未通过 |
| 通过（低置信） | 置信度不能改变判定 | 补证到达标；补不到就写未通过 |
| 除少数场景外都通过 | 少数场景没有证据也没说明 | 列出未覆盖场景，写未通过或阻塞 |

`带欠账` 和 `带欠账交付` 只为读取历史账本保留，读取时需显式加 `--compat-debt`；新账本、新项目合同不得使用。它们不是绕过 v1 三包结论（或旧八列三态）的通用写法；`--strict` 会叠加拒绝并报 `E_STRICT_DEBT`。

唯一例外不存在：只要还有一项没有达标证据，整体就不能写通过。

## 7. 完成审计（收口前）

包结论之前，必须把完成定义逐条对到下面这张表；缺一条不得写“通过”。

| 完成定义 | 实际场景 / 命令 | 最终构建 | 读数 | 证据 |
|---|---|---|---|---|
| … | … | … | … | … |

- 旧构建、旧日志、旧截图不能替代最终构建的复验。
- 能现在补的验证、补证、修复，不留给下一轮；`未覆盖` / `带欠账` 不是默认终态。
- 交付物必须自包含：任务卡、07、证据、引用文件都在提交里；干净检出能复现。
- 基础设施失败一次就换通道：模型服务错误、注入失败、任务失败，换会话/模型/注入方式，不重复撞墙。

## 8. 多批次编排（调度方）

一个工程拆成多批串行跑时，调度方按本节执行；单批内部仍走 `SKILL.md` 的五步流程。

### 8.1 批次类型

| 类型 | 产出 | 改代码 |
|---|---|---|
| 准备批 | 逐条复验结论 + 缺陷档案（01/02）+ 复核总表 | 否 |
| 修复批 | 修复提交 + 逐条改前改后证据 + 账本 + 标签 | 是 |
| 回归批 | 全量回归矩阵 + 版本结论 | 一般否 |

修复批的输入就是准备批的复核总表：表里每条“真缺陷”对应一条 AC，档案目录直接抄进任务书。

**一次收到 ≥3 条用户反馈时，第一批必须是准备批**：只复验、只建档、不改代码；复验结论和复核总表作为修复批的输入，不允许跳过准备批直接修。

### 8.2 角色与串行约束

- 调度会话：写任务书、挂巡检、判放行、修缺口、派下一批、给版本结论；不写产品代码，不在批次运行中改它的工作区。
- 批次会话：只做本批，产出代码、证据、账本、标签；不做别的批次，不自行 push，不替自己签字。
- 上下文不继承，交接只靠任务书、提交、证据、账本。任务书不许写“见上一批”。
- ⛔ 同一工作区不许并行跑两批：提交、证据、门禁全会对不上。要快就串行，批内用子代理并行。

### 8.3 每批五步

1. 用一次性定时任务拉起新会话，任务书全文或文件路径作为启动指令。
2. 同时给新会话挂每 15 分钟只读巡检，暂停上一批的巡检。
3. 巡检读会话原始记录 + 仓库实际状态，两层汇报（三行结论 / 技术细节）。
4. 会话结束按放行五条判定。
5. 全绿派下一批；不绿先按三类缺口修，修完复跑门禁再派。

### 8.4 放行五条（缺一不可）

1. 批次标签存在，解引用后等于最终提交。
2. 账本包结论“通过”，没有未交付-失败 / 未交付-阻塞。
3. 独立复核逐项签字，签字人是真实子代理会话，且有 `verifier-run.json`（session id、复跑时间、退出码、HEAD）。复核会话核验由 `scripts/check_reviewer.py` 执行（`gate --verify-reviewer`），核对会话目录、创建时间、复核独立性和退出码。
4. 四道门禁全绿：`doctor` 全过、覆盖总表全部已覆盖、证据检查 exit 0、总门禁 5/5。总门禁必须带 `--coverage`；显示“覆盖总表：未配置（跳过）”的 5/5 不算。
5. `git status --short --untracked-files=all` 为空。

### 8.5 三类缺口

| 缺口 | 处理 |
|---|---|
| 证据缺或读数不成立 | 重跑设备取证，补证据文件，账本按新读数重写 |
| 账本、任务卡、旅程卡写错或漏项 | 按真实读数改文档，⛔ 不许改判据迁就结论 |
| 产品有缺陷 | 先复现、打日志、改代码、设备复验、补缺陷档案，再重跑门禁 |

修不动的写清卡点和一句话解锁条件后停下。

### 8.6 三条红线

1. **设备写死**：不写机型会开错模拟器；平板环境里不要放“真鼠标右键”这类电脑判据。
2. **复核必须真会话**：主代理自己填 `xxx-verifier` 不算。核实办法：去 `~/.dsh/sessions/` 找该 id 的目录，查不到、创建时间晚于批次结束、或不是本批次的子会话，一律判自签。
3. **账本先读数后结论**：先写“通过”再拿校验器报错反推格式，最后一定变成凑格式。

### 8.7 任务书八段

目标 / 当前状态（基线、工作区、已完成、不要重做）/ 环境与参数（设备写死）/ 完成定义 / 任务分组（按依赖排序）/ 证据规则 / 边界 / 汇报格式。

修复批另加“回归范围”：受影响路径 + 上游已修项抽验至少 3 条 + 视口/主题/语言档位。

最小骨架：

```text
# 批次任务书：<批次名>
0. 你是谁、做什么：只做本批；基线 <标签/提交>；完成即停。
1. 环境与硬约束：设备 <地址/机型/分辨率>；禁宿主级输入注入；组合键先正对照。
2. 本批范围：AC 表（AC | 缺陷/需求 | 判据）。
3. 怎么做：侦察 ≤20 分钟 → 按组实现 → 分组最小验证 → 合并回归。
4. 证据：脚本路径、JSON 字段、改前/改后图、控件树/像素/DB 读数。
5. 输入通道正对照：<设备上点得动/输得进的证明；证明不了记未覆盖>
6. 复核：<谁签、会话 id 怎么核、verifier-run.json 放哪>
7. 账本：13 列、包结论、独立复核（真会话 id）、完成审计、欠账、阻塞举证。
8. 验证命令：doctor / check_coverage / check_evidence / gate（带 --coverage --team --base）。
9. 提交与 tag：产品与证据分开；v<版本>-batch-<n>；不 push。
10. 节奏：单条 15 分钟无读数跳下一条；同一动作不撞第三次。
11. 边界：不启动其他批次；不动历史批次资产；不新增依赖。
12. 汇报：改了什么 / 验证证据 / 风险 / 待办；结论三选一。
```

### 8.8 收尾

- 版本级结论三选一：通过 / 带欠账交付 / 未交付（失败或阻塞）。
- 批次标签统一 `v<版本>-batch-<n>`；语义不清的标签不许打。
- 推送、改历史、删标签单独授权，不默认做。
- 未覆盖项单列，写清是环境限制还是没做，不算进通过。
