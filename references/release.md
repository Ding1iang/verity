# 发布模式

> 发布不是“代码写完”，而是“这一批可以对外”。验收账本、版本说明、回滚点三件事必须同时成立。

## 0. 适用边界与前置

用于一批改动准备交付给用户或外部环境时。日常提交、内部合并和未验收的中间版本不走发布。

**发布前硬门槛**：

- `07-验收回归清单.md` 的结论是“通过”，所有验收项为通过或不适用。
- 没有待验、验中、待定、未通过或阻塞项。
- 每条证据都锚定到本次发布的 commit 或构建号，没有复用旧版本的结论。
- 发布范围已冻结，版本号和更新日志已定稿。

任何一条不满足，回到对应模式补齐；发布模式不负责修缺陷，也不负责补验收。

## 1. 发布流水线

| 步骤 | 动作 | 产出 | 出口条件 |
|---|---|---|---|
| 1 冻结范围 | 确认这一版只包含哪些改动 | 发布范围清单 | 范围外改动不进入本版 |
| 2 定版本号 | 按变更性质确定版本 | 版本号与版本源文件 | 版本号唯一、可追溯 |
| 3 写更新日志 | 只写用户可感知的变化 | 更新日志对应版本一节 | 非开发者能读懂，无内部术语 |
| 4 发布前检查 | 逐项核对验收、构建、安全、回滚 | 检查表与证据 | 全部通过，无缺证项 |
| 5 建回滚点 | 记录上一可用版本和恢复方法 | 回滚点记录 | 恢复步骤可执行、可复验 |
| 6 构建与发布 | 从干净检出构建，打标签并发布 | 构建产物、标签、发布记录 | 产物 hash 与标签一致 |
| 7 发布后验证 | 按用户入口做冒烟检查 | 冒烟结果 | 通过则归档；失败则回滚 |

## 2. 版本号

采用语义化版本 `MAJOR.MINOR.PATCH`：

| 变更性质 | 升哪一位 | 例子 |
|---|---|---|
| 不兼容变更：删除能力、改变数据格式且不提供迁移 | MAJOR | `1.4.0 → 2.0.0` |
| 向后兼容的新能力 | MINOR | `1.4.0 → 1.5.0` |
| 向后兼容的缺陷修复、文案或小改进 | PATCH | `1.4.0 → 1.4.1` |
| 预发布 | 加后缀 | `1.5.0-rc.1` |

规则：

- 版本号只有一个来源：版本文件或包清单。标签、更新日志、发布说明都引用它，不各写一份。
- 标签格式固定为 `v<版本号>`，指向本次发布的 commit；标签一旦发布，不移动、不重用。
- 先定版本号，再写更新日志；版本号变了，更新日志里的版本标题同步改。
- 已经发布过的版本号不能复用。发现版本号错了，发新版本并在更新日志里说明，不改旧标签。
- 不确定升哪一位时，按影响更大的那一级升；不把不兼容变更藏在 PATCH 里。

## 3. 更新日志

### 3.1 只写用户可感知的变化

判断标准只有一句：**用户会不会在使用中遇到不同？**

| 改动 | 用户可感知 | 写不写 |
|---|---|---|
| 新增一个入口、命令或能力 | 是 | 写“新增” |
| 已有行为、结果或默认值改变 | 是 | 写“改进”或“修复” |
| 之前会失败、现在能成功 | 是 | 写“修复” |
| 界面文案、布局、提示变化 | 是 | 写“改进” |
| 内部重构、改名、分层调整 | 否 | 不写 |
| 只加测试、CI、注释或开发脚本 | 否 | 不写 |
| 依赖升级但行为不变 | 否 | 不写 |
| 性能提升且用户能感知 | 是 | 写“改进”，有实测才写数字 |

更新日志不是提交日志。提交里有的内部改动，不必出现在更新日志里；更新日志里也不能出现用户看不懂的实现细节。

### 3.2 写法

1. **一条一句**：一条只讲一个变化，不把三项改进塞进一句。
2. **用用户的话**：不写文件名、函数名、类名、提交号、测试编号、内部代号。
3. **有对照写对照**：此前怎样、现在怎样；纯新增写“现在可以……”。
4. **不写空话**：“优化体验”“修复若干问题”“提升稳定性”都不合格，必须说清具体变化。
5. **同一变化只写一次**：不按模块重复，不在“新增”和“改进”各写一遍。
6. **写不出人话就说明改动太杂**：先拆清变化，再写说明。

| 不合格 | 为什么不合格 | 合格写法 |
|---|---|---|
| 重构导出模块，修复 NPE | 用户不知道 NPE 是什么 | 导出标题含特殊字符的文件时不再失败 |
| 优化搜索性能 | 没有说清用户感受到什么 | 搜索一万条内容时，结果出现时间从约 3 秒降到 1 秒内（有实测才写数字） |
| 修复了保存问题 | 太笼统，用户不知道何时会遇到 | 断网时保存失败，现在会提示并保留草稿 |
| 升级依赖，修复若干问题 | 用户不可感知，且没有具体信息 | 不写；如果有具体缺陷，按缺陷写 |
| 新增 XX 能力，优化 YY 流程，修复 ZZ 问题 | 一句话三件事，读者记不住 | 拆成三条，各写各的 |

### 3.3 根据一次改动写说明的三步

1. **找差异**：用户操作前和操作后，看到的结果有什么不同？找不到差异，就不写进更新日志。
2. **写对照**：用“此前……现在……”或“现在可以……”写一句完整的话。
3. **删内部词**：把文件名、函数名、提交号、测试编号、内部术语全部删掉；读给不写代码的人听，能复述才算过。

示例：

```text
改动：标题转链接时，按长度截断会在末尾留下一个连字符。
更新说明：标题转链接时，按长度截断不再留下末尾横杠。
```

## 4. 发布前检查

逐项核对并留下证据；任何一项没有证据，按未通过处理，不发布。

| 检查项 | 判据 | 证据 |
|---|---|---|
| 验收结论 | 07 结论为通过，计数与账本一致 | 07 路径与收口行 |
| 证据锚点 | 所有证据指向本次发布 commit 或构建号 | 账本“被测版本”列 |
| 版本一致 | 版本文件、标签、更新日志标题三处一致 | 文件路径、标签名 |
| 干净构建 | 从干净检出构建成功，无未提交改动 | 构建命令与结果 |
| 产物可追溯 | 构建产物 hash 已记录，与发布产物一致 | hash 读数 |
| 安装与启动 | 按用户入口安装或启动成功 | 冒烟步骤与结果 |
| 关键路径 | 主路径、错误路径各至少一次冒烟 | 操作路径与读数 |
| 更新日志 | 只含用户可感知变化，无内部术语 | 更新日志对应版本 |
| 安全与隐私 | 无密钥、令牌、个人信息、内部地址 | 扫描命令与结果 |
| 回滚点 | 上一可用版本、恢复步骤和验证方式齐全 | 回滚点记录 |
| 独立复核 | 发布检查由非执行者复核 | 复核人签字或记录 |
| 已知限制 | 未覆盖范围已写明，不藏在“通过”里 | 发布说明的限制一节 |

## 5. 回滚点

回滚点必须在发布前建立，不是出事后再想。

| 项目 | 必须写清 |
|---|---|
| 上一可用版本 | 版本号、标签、commit |
| 产物 | 上一版构建产物路径或下载地址、hash |
| 数据 | 是否涉及数据迁移；备份位置；能否回退 |
| 恢复步骤 | 停止什么、替换什么、执行什么命令、按什么顺序 |
| 恢复后验证 | 用哪条冒烟检查确认恢复成功 |
| 触发条件 | 什么现象触发回滚，谁来决定 |
| 预计恢复时间 | 从决定回滚到恢复可用的时间 |

规则：

- 回滚点要实际演练或在临时环境走一遍；没演练就写“未验证”，不能声称“可随时回滚”。
- 涉及数据迁移时，先备份；只能向前迁移的，必须在发布说明里写明不可回滚及补救方式。
- 回滚用上一版产物或 revert 提交，不在共享分支上做 `git reset --hard` 或改写历史。
- 回滚后同样要跑冒烟检查，确认旧版本真的可用。

## 6. 发布执行与失败处理

执行顺序：

1. 冻结发布范围，之后的改动只能作为新的修复进入下一版；如必须进入本版，重跑受影响的验收和检查。
2. 从干净检出构建，记录构建命令、环境和产物 hash。
3. 核对产物与标签指向同一个 commit。
4. 打标签并发布；发布动作和权限按项目规定执行。
5. 发布后按用户入口做冒烟检查，记录时间和结果。
6. 归档 07、更新日志、发布记录和回滚点。

发布后冒烟失败：立即回滚，发布结论记“失败”，写清失败现象、影响范围和回滚结果。不要用“先发着，稍后热修”掩盖；热修也要走同一套验收和发布检查。

## 7. 发布记录

一次发布至少留下：

- 版本号、标签、commit、产物 hash。
- 发布时间、执行者、复核者。
- `07-验收回归清单.md` 路径与结论。
- 更新日志的版本小节。
- 回滚点及是否演练。
- 发布后冒烟结果。
- 已知限制或未覆盖范围。

## 8. 常见失败

| 失败形态 | 后果 | 正确动作 |
|---|---|---|
| 代码写完就发布 | 未验项被带出门 | 先让 07 收口为通过 |
| 版本号随手加一 | 不兼容变更被当成小修复 | 按变更性质定 MAJOR/MINOR/PATCH |
| 更新日志写成提交日志 | 用户看不懂，也不知道自己会遇到什么 | 只写用户可感知的变化，删内部词 |
| 回滚点只写“上一版” | 真出事时找不到产物和步骤 | 写版本、hash、命令、验证方式并演练 |
| 发布后发现问题直接热修 | 没有记录，问题可能重复 | 先回滚或按发布流程发补丁版 |
| 更新日志漏掉用户可见变化 | 用户升级后遇到意外 | 每次改动都过一遍“用户会不会遇到不同” |

## 9. 收口自检

- [ ] 07 结论为通过，计数与账本一致，证据锚定本次发布。
- [ ] 版本号按变更性质确定，版本文件、标签、更新日志三处一致。
- [ ] 更新日志只写用户可感知变化，非开发者能读懂。
- [ ] 发布前检查每项都有证据，没有缺证项。
- [ ] 回滚点有版本、产物 hash、恢复步骤和验证方式，且已演练或明确标注未验证。
- [ ] 干净构建和发布后冒烟都通过。
- [ ] 发布记录已归档，已知限制已写明。
